# SourceView scrolling: synchronization waits

Investigation of [#83](https://github.com/anesthetised/agenthesia/issues/83), based on `6f4c8a9`.
No product rendering strategy or dependency is changed by this investigation.

## Finding

Several long scroll intervals coincide with the main thread waiting in:

```text
mach_msg2_trap
CA::Render::Context::wait_for_synchronize
CA::Context::synchronize
CABackingStoreSynchronize
CABackingStorePrepareUpdates_
CABackingStoreUpdate_
CA::Layer::display_if_needed
CA::Transaction::commit
```

CPU-only sampling obscured this: the recorded 100–171 ms gaps contained only 4–11 ms of main-thread
CPU sample weight. Recording waiting threads and context switches exposed long synchronous waits in
Core Animation's backing-store update path. These are observed blocking sites, not proof of which
layer, dependency behavior, compositor condition or OS defect causes the waits.

| Recording | Display interval | Callback interval | Selected synchronization wait weight |
|---|---:|---:|---:|
| SourceView, colors and line numbers | 153.36 ms | 153.09 ms | 140.13 ms |
| SourceView, colors and line numbers | 170.56 ms | 169.35 ms | 141.91 ms |
| SourceView, neither colors nor line numbers | 157.97 ms | 151.67 ms | 149.06 ms |
| SourceView in a separate AppKit window | 308.20 ms | 303.82 ms | See correlated samples; multiple waits |

The gap markers and samples share the recording's time axis. The marker is emitted on callback entry;
its callback duration identifies the preceding callback-to-callback interval. Sample weights with
waiting-thread recording enabled are **not CPU time**. Boundary samples and sampling granularity also
mean their sum is not an exact wall-clock decomposition. See [correlated-waits.json](correlated-waits.json)
and the separately recorded [CPU-only gaps](cpu-only-gaps.json).

The waits recur without syntax colors and without the gutter. They also recur when SourceView has no
SwiftUI hosting ancestors. The AppKit-host control still runs inside the Agenthesia application;
it does not remove SwiftUI from the process or prove that STTextView alone causes the issue.

## Controls and limits

Same MacBookPro18,2, 32 GiB, macOS 27.0.1, Xcode 27 / Swift 6.4, 120 Hz screen, 2x scale and an
868 x 340 pt viewport as the earlier investigation. Runs were sequential on an ordinary desktop,
not an isolated performance machine. No other build or benchmark was deliberately run concurrently.
System load varied, especially after building. These controls establish hypotheses, not a performance win.

The first unprofiled sweep, one fresh process per configuration, gave maximum display intervals of
123.61 ms (colors + lines), 105.57 ms (colors), 128.35 ms (lines), and 42.01 ms (neither).
All p95 values were 8.33 ms. [controls.json](controls.json) retains environment and per-run results.
The later plain-view profile reached 157.97 ms: a single quiet run does not exclude an intermittent stall.

A standalone [native probe](native-probe.swift), using AppKit's `NSTextView` with TextKit 2 and no
Agenthesia modules, STTextView, SwiftUI, gutter or highlighter, completed three profiled traversals:
maximum display intervals **35.99, 24.52 and 49.46 ms**. All reached the document end and confirmed
TextKit 2 was active. See [native-results.json](native-results.json).

This is an isolation control, not a replacement proposal or a directly comparable rendering benchmark:
it has a different view hierarchy and line metrics. The same 10,000-line fixture is copied into the
self-contained probe; the native document height was 150,001 pt. It does not implement SourceView's
features or establish their behavior on NSTextView.

All profiles here use programmatic scrolling at 7,200 pt/s. STTextView has a separate live-scroll size
update policy; these results do not establish the behavior of trackpad gestures. Raw `.trace` bundles
and exported XML remain local under `.build/`; the committed JSON contains the relevant summaries.
[profiles.json](profiles.json) records the source-view results used above.

## Reproduction

Agree on resource use before running. Each recording is a fresh process, at most 30 seconds. Keep the
lab visible, run sequentially, and use a new trace path each time. The saved recording options were
generated by Xcode 27; regenerate them with that toolchain's `xctrace --show-recording-options` if needed.

```sh
just lab-profile S4:lines+colors .build/source-waits.trace docs/benchmarks/2026-10-07/source-scroll/wait-options.json
just lab-profile S4: .build/plain-waits.trace docs/benchmarks/2026-10-07/source-scroll/wait-options.json
just lab-profile S4:appkit+lines+colors .build/appkit-waits.trace docs/benchmarks/2026-10-07/source-scroll/wait-options.json
just lab-profile-export .build/source-waits.trace .build/source-waits-cpu.xml
just lab-profile-export .build/source-waits.trace .build/source-waits-events.xml PointsOfInterestEvents
just --working-directory . --justfile docs/benchmarks/2026-10-07/source-scroll/reproduce.just profile .build/native-waits.trace
```

`LongFrame` marks display or callback intervals above 50 ms. This diagnostic threshold is independent
of the refresh-budget hitch metric; it does not change the benchmark's scoring. The `Scenario` interval
and gap events use the Points of Interest category so the profiling recipe actually captures them.
Inspect a marked interval in Instruments, including waiting stacks, before attributing it to a CPU hotspot.

## Next decision

STTextView 2.4.1 (`bbdcfd9d413ad3055dafd23a223be9bd39742f89`) assigns the layout fragment back to a
cached fragment view in `configureRenderingSurfaceFor`. The fragment property's setter unconditionally
sets `needsDisplay` and `needsLayout`, even for the same object. This is a candidate source of redundant
backing-store updates, **not an established cause of these waits**. A same-object guard alone may leave
stale rendering because a fragment can change internally; text edits, color changes, selection,
attachments and spelling decorations require explicit validation.

Recommend a bounded, dependency-focused prototype to test redraw invalidation and identify the affected
layer before proposing an upstream fix or pinning a fork. Alternative local layer-policy changes may
reduce waits but require their own correctness and performance evidence. Replacing STTextView with
NSTextView would be a larger architectural change and is not justified by this control alone.

Discuss the implementation path with the owner. Keep #83 open: this investigation localizes observed
stalls and improves the diagnostics; it does not fix scrolling or prove every historical outlier has
the same cause.
